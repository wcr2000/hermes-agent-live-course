# แนวทางผู้สอน
[กลับหน้าแรก](../README.md)

## หลักการออกแบบ repo นี้
- ผู้เรียนเลือก **คืน** ก่อน แล้วอ่าน `README.md` เป็นทางเข้าของคืนนั้น
- เนื้อหาใน repo **เรียงตามสไลด์แบบหน้าต่อหน้า** — สไลด์ใช้เล่า repo ใช้อ่านย้อน
- ใช้โจทย์จริงของผู้เรียนเป็นแกนตลอดห้าคืน · [`project/`](../project/README.md) เป็นทางสำรองเท่านั้น
- ทุกคืนจบด้วย **ไฟล์** ไม่ใช่ความเข้าใจ — `MEMORY.md` → `SKILL.md` → `workflow.md` + `team.md` → `EMPLOYEE.md`

## จังหวะสอนในคลาส
```
เปิด README → บอกผลลัพธ์ปลายคืน → อธิบายภาพ → สาธิต → ให้ทำตาม → หยุดตรวจ checkpoint
```
ระหว่าง Workshop ให้ชี้ไปที่ `workshop.md` — Prompt ทุกอันคัดลอกไปวางได้เลย ไม่ต้องพิมพ์ตาม

## ก่อนคลาสแต่ละคืน
1. เลือก Hermes version และ model แล้วเติม [บันทึกการทดสอบ](../resources/tested-environment.md)
2. ซ้อม Workshop ของคืนนั้นจากเครื่องสะอาดตามทุกขั้น
3. เติม integration จริงเฉพาะที่จะสอน — ที่ยังไม่ซ้อมให้บอกตรง ๆ ว่าเป็น demo pending
4. ใส่ภาพผลลัพธ์ที่ปกปิดข้อมูลลับไว้ข้างขั้นตอน
5. สร้าง release ของเอกสารสำหรับรุ่นเรียน เช่น `cohort-2026-09-v1`

## จุดที่ผู้เรียนมักตกในแต่ละคืน

| คืน | จุดที่ตก | วิธีช่วย |
|---|---|---|
| 1 | เชื่อว่า Agent สร้างไฟล์แล้ว โดยไม่เปิดดู | ให้ทุกคน `ls` โฟลเดอร์พร้อมกันหนึ่งครั้ง |
| 2 | เขียน Memory กว้างจนตรวจไม่ได้ | ให้อ่านบรรทัดของตัวเองแล้วถามว่า “ทำตามหรือไม่ทำตาม” |
| 3 | Skill เรียกไม่ติดด้วยภาษาคน (รอบที่ 2) | ให้ไปแก้ `description` ไม่ใช่แก้ Process |
| 4 | ตอบ ok ผ่าน ๆ ตอน Agent เสนอแผน | หยุดห้องหนึ่งนาที ให้ทุกคนอ่านแผนของตัวเองจริง ๆ |
| 5 | ทดสอบแต่กรณีที่ทำงานได้ | บังคับให้ทุกคนรันรอบที่ 3 (คำสั่งนอกขอบเขต) ก่อนเดโม |

## หลังคลาส
- แก้ข้อผิดพลาดใน Markdown แล้วจดใน [CHANGELOG](../CHANGELOG.md)
- ไม่เปลี่ยนชุดคำสั่งกลางคลาสโดยไม่ประกาศ
- อัปโหลดสไลด์ของคืนนั้นลง [`slides/`](../slides/README.md)
- สร้าง tag checkpoint หลังซ้อมแต่ละคืน เพื่อให้ย้อนกลับได้
