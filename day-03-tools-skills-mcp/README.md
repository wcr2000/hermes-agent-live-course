## Session 5 · Tools & Tool Calling (20:00 – 20:30)

### จาก “ตอบได้” เป็น “ทำได้”

| | ไม่มี Tool · Model ที่รู้แต่ไม่ทำ | มี Tool · Agent ที่เปลี่ยนสภาพแวดล้อม |
|---|---|---|
| ผลลัพธ์จบที่ไหน | ข้อความในหน้าจอ | ไฟล์ในโฟลเดอร์ของเรา |
| ตรวจย้อนหลังได้ไหม | ได้แค่อ่านคำตอบซ้ำ | ตามได้ว่าอ่านอะไร สั่งอะไร ได้อะไรกลับ |
| เมื่อข้อมูลเปลี่ยน | ต้องเล่าให้ฟังใหม่ทั้งหมด | สั่งให้ไปอ่านใหม่ แล้วมันทำเอง |

โมเดลตัวเดียวกันทั้งสองฝั่ง — สิ่งที่เพิ่มเข้ามาคือ **สิทธิ์ในการอ่านไฟล์** และ **หน้าที่ต้องอ่านผลก่อนสรุป**

### Tool Calling ทำงานอย่างไร

```
1 เข้าใจโจทย์ → 2 เลือกเครื่องมือ → 3 เรียกเครื่องมือ → 4 อ่านผลจริง → 5 ตัดสินใจขั้นถัดไป
                         ↑                                                        │
                         └──────────────── วนได้หลายรอบในงานเดียว ────────────────┘
```

ขั้นที่ 4 คือหัวใจ — Agent ต้องอ่านผลลัพธ์จริงก่อนตัดสินใจขั้นถัดไป ไม่ใช่เดาว่าคำสั่งสำเร็จ
ถ้ามันข้ามขั้นที่ 4 ไปตอบเลย นั่นคือจุดที่คำตอบเริ่มเป็นการเดาที่เขียนสวย

### Agent มองเห็น Tool เป็นอย่างไร
Agent ไม่เห็นโค้ดของเครื่องมือ — เห็นแค่ป้ายชื่อสามบรรทัดนี้ แล้วตัดสินใจจากมัน

| ส่วน | ตัวอย่าง | ทำไมถึงสำคัญ |
|---|---|---|
| **name** · ชื่อที่ใช้เรียก | `read_file` | สั้น ตรงตัว สื่อว่าทำอะไร — ชื่อคลุมเครือทำให้ Agent เรียกผิดตัว |
| **description** · ใช้เมื่อไร | “อ่านเนื้อหาไฟล์จาก path ที่ระบุ ใช้เมื่อต้องดูข้อมูลจริงก่อนตอบ” | บรรทัดที่สำคัญที่สุด — Agent เลือกเครื่องมือจากประโยคนี้เป็นหลัก |
| **parameters** · ต้องกรอกอะไร | `path: string (บังคับ)` · `lines: number (ไม่บังคับ)` | ถ้าไม่ระบุว่าอะไรบังคับ Agent จะเดา แล้วเรียกพลาดรอบแรกเสมอ |

### เดินตามลูปจริง หนึ่งงาน
โจทย์ · “สรุปว่าไฟล์ log เมื่อคืนมี error กี่ครั้ง และเป็นเรื่องอะไร”

| รอบ | Agent คิดอะไร | เรียกเครื่องมือ | ได้อะไรกลับมา |
|---|---|---|---|
| 01 | ยังไม่รู้ว่าไฟล์อยู่ไหน ต้องดูก่อน | `list_dir("logs/")` | พบ `app-0913.log` ขนาด 4.2 MB |
| 02 | ไฟล์ใหญ่เกินกว่าจะอ่านทั้งก้อน | `grep("ERROR", "app-0913.log")` | เจอ 37 บรรทัดที่ตรงเงื่อนไข |
| 03 | 37 บรรทัดพอไหว อ่านของจริง | `read_lines(ทั้ง 37 บรรทัด)` | ข้อความ error เต็ม ๆ พร้อมเวลา |
| 04 | จัดกลุ่มดูว่าซ้ำเรื่องเดียวกันไหม | — คิดเอง ไม่ต้องใช้ tool — | 3 กลุ่ม · timeout 29 · auth 6 · อื่น 2 |
| 05 | ส่งเป็นไฟล์ให้เปิดอ่านย้อนได้ | `write_file("error-summary.md")` | ไฟล์จริงในโฟลเดอร์ พร้อมเวลาและตัวอย่าง |

> สังเกตรอบที่ 2 — Agent เปลี่ยนวิธีเพราะเห็นว่าไฟล์ใหญ่เกินไป นั่นคือการอ่านผลลัพธ์จริง ไม่ใช่เดา

### เครื่องมือสี่กลุ่มที่ใช้คืนนี้

| กลุ่ม | ทำอะไร | ตัวอย่างงาน |
|---|---|---|
| **File System** | อ่าน เขียน และจัดโครงสร้างไฟล์ใน Workspace | อ่าน `sales.csv` 1,204 แถว · สร้าง `report.md` · ดูว่าในโฟลเดอร์มีอะไรบ้าง |
| **Terminal** | รันคำสั่งจริงและอ่าน Output กลับมาใช้ต่อ | `grep` หา ERROR ใน log · รันเทสแล้วอ่านผล · แปลงไฟล์ด้วยคำสั่งเดียว |
| **Search** | ค้นข้อมูลใหม่ที่ไม่มีอยู่ใน Context ของ Model | ราคาคู่แข่งสัปดาห์นี้ · ประกาศที่เพิ่งออกเมื่อวาน · เอกสารเวอร์ชันล่าสุด |
| **API** | ดึงและส่งข้อมูลกับระบบอื่นตามสิทธิ์ที่ได้รับ | ดึง Issue จากระบบทีม · อ่านตัวเลขจากฐานข้อมูล · ส่งสรุปเข้าห้องแชท |

### งานแบบนี้ ใช้เครื่องมือไหน

| งาน | เครื่องมือ | หมายเหตุ |
|---|---|---|
| อยากรู้ว่ามีไฟล์อะไรบ้าง | File System | `list` / `glob` — อย่าเพิ่งอ่านเนื้อหา |
| หาคำหรือรูปแบบในไฟล์จำนวนมาก | Terminal | `grep` เร็วกว่าให้ Agent ไล่อ่านทีละไฟล์มาก |
| ต้องเข้าใจเนื้อหาไฟล์จริง ๆ | File System | อ่านเฉพาะช่วงที่ต้องใช้ ไม่ใช่ทั้งไฟล์ |
| ข้อมูลใหม่กว่าที่โมเดลรู้ | Search | ข่าว ราคา ประกาศ เอกสารที่เพิ่งออก |
| ต้องได้ตัวเลขจากระบบของเรา | API | ดึงตามสิทธิ์ที่ได้รับ อย่า copy ข้อมูลมาวางในแชท |
| ต้องรัน ต้องทดสอบ ต้องแปลงไฟล์ | Terminal | สั่งแล้วอ่าน output กลับมาตัดสินใจต่อ |

> หลักง่าย ๆ — **แคบก่อนค่อยลึก · หาให้เจอก่อนแล้วค่อยอ่าน · อ่านเท่าที่ต้องใช้**

### สี่อาการที่เจอบ่อย และทางแก้
เกือบทุกครั้งที่ Agent “ทำไม่ได้” คือหนึ่งในสี่ข้อนี้ ไม่ใช่โมเดลไม่เก่ง

| อาการ | ทางแก้ |
|---|---|
| Agent ตอบว่าทำเสร็จแล้ว แต่ไม่มีไฟล์ | สั่งให้ยืนยันด้วยการ `list` โฟลเดอร์ แล้วอ่านไฟล์กลับมาให้ดู |
| เรียกเครื่องมือเดิมวนซ้ำไม่จบ | หยุดแล้วถามว่า “ตอนนี้ติดอะไร” — ให้มันสรุปสถานะก่อนไปต่อ |
| ขอสิทธิ์ทุกคำสั่งจนทำงานไม่ลื่น | อนุญาตล่วงหน้าเฉพาะคำสั่งอ่านอย่างเดียว เก็บการถามไว้ให้คำสั่งที่เขียนทับ |
| ผลลัพธ์ยาวจน Context เต็มแล้วลืมโจทย์ | ให้กรองก่อนอ่าน เขียนผลลงไฟล์ แล้วอ้างถึงไฟล์แทนการวางเนื้อหา |

> เก็บวิธีแก้ที่ได้ผลไว้ — พอมันซ้ำรอบที่สาม นั่นคือสัญญาณว่าควรเขียนเป็น **Skill**

### Permission และ Security
ยิ่ง Agent ทำได้มาก ความเสี่ยงยิ่งย้ายจาก *คำตอบผิด* ไปเป็น *การกระทำผิด* — ก่อนเข้า Workshop จึงต้องตกลงขอบเขตให้ชัด

1. **กำหนด Workspace ให้ชัด** และให้ Agent ทำงานอยู่ในขอบเขตนั้น — โฟลเดอร์เดียว จบในนั้น
2. **แยกคำสั่งที่ทำได้เอง ออกจากคำสั่งที่ต้องขออนุญาตก่อน** — เส้นแบ่งอยู่ที่ “ย้อนกลับได้ไหม”
3. **ไม่ใส่ Credential จริงลงใน Context** หรือไฟล์ที่ Agent อ่านได้ — ให้ชื่อ Environment Variable ไป อย่าให้ค่าจริง
4. **ให้ Agent สรุปสิ่งที่ทำไปทุกครั้ง** เพื่อให้ตรวจย้อนหลังได้

### แบ่งสิทธิ์เป็นสามระดับ

| ALLOW · ทำได้เอง | ASK · ถามก่อน | NEVER · ห้ามเด็ดขาด |
|---|---|---|
| อ่านไฟล์ในโฟลเดอร์งาน | เขียนทับหรือลบไฟล์ | แตะ Production โดยตรง |
| ค้นหาข้อความ · ดูรายชื่อไฟล์ | ติดตั้งอะไรลงเครื่อง | ใช้ Credential จริงในแชท |
| รันคำสั่งที่ไม่แก้ของ | เรียก API ที่เปลี่ยนข้อมูล | ส่งข้อมูลลูกค้าออกนอกระบบ |
| ค้นเว็บสาธารณะ | ส่งอะไรออกนอกเครื่อง | ลบทั้งโฟลเดอร์ |
| *พลาดแล้วไม่เสียหาย · ย้อนได้ทันที* | *ย้อนได้ แต่ต้องรู้ตัวก่อน* | *พลาดครั้งเดียวย้อนไม่ได้* |

> ตกลงสามระดับนี้กับตัวเองก่อนเข้า Workshop — แล้วบอก Agent ตรง ๆ ในบรรทัดแรกของงาน

## Session 6 · Custom Skills (21:10 – 21:30)

### Skill ต่างจาก Prompt อย่างไร

| | Prompt · คำสั่งครั้งเดียว | Skill · วิธีทำงานที่เก็บไว้ |
|---|---|---|
| อยู่ได้นานแค่ไหน | จบเมื่อปิด Session | อยู่ถาวรจนกว่าจะแก้ |
| ใครใช้ได้ | คนที่จำได้ว่าเคยสั่งอย่างไร | ทุกคนในทีมที่เรียกชื่อมันได้ |
| แก้ให้ดีขึ้นตรงไหน | แก้ทีละครั้ง แล้วก็หายไป | แก้ที่ไฟล์เดียว ดีขึ้นทุกครั้งที่เรียก |

Skill คือ **Procedural Memory** ที่ Agent หยิบมาใช้เมื่อเจองานประเภทเดิม

### งานแบบไหนควรทำเป็น Skill

| ✓ สัญญาณว่าควรเขียน | ✕ สัญญาณว่ายังไม่ต้อง |
|---|---|
| ทำซ้ำอย่างน้อยสัปดาห์ละครั้ง | ทำครั้งเดียวแล้วจบ |
| มีลำดับขั้นที่ค่อนข้างตายตัว | ทุกครั้งวิธีทำไม่เหมือนกันเลย |
| คนอื่นในทีมก็ต้องทำงานนี้เหมือนกัน | ยังไม่รู้ว่าผลลัพธ์ที่ดีหน้าตาเป็นยังไง |
| ผลลัพธ์ต้องหน้าตาเหมือนเดิมทุกครั้ง | เป็นแค่คำสั่งสั้น ๆ ที่พิมพ์ใหม่ก็เร็วพอ |
| เราเคยอธิบายวิธีทำให้ Agent ฟังมาแล้วหลายรอบ | ขั้นตอนยังเปลี่ยนทุกสัปดาห์ — รอให้นิ่งก่อน |

> เริ่มจากงานเดียวที่น่าเบื่อที่สุดในสัปดาห์ — นั่นคือ Skill แรกที่คุ้มที่สุดเสมอ

### โครงสร้างของ SKILL.md

| ส่วน | คำถามที่ต้องตอบให้ได้ |
|---|---|
| **Input** · รับอะไรเข้ามา | ต้องมีอะไรอยู่แล้วถึงจะเริ่มได้ · ถ้าไม่มีจะทำอย่างไร |
| **Process** · ทำตามขั้นตอนไหน | ทำอะไรก่อนหลัง · ตรงไหนต้องหยุดถาม · อะไรที่ห้ามทำ |
| **Output** · ส่งอะไรกลับ | ไฟล์ชื่ออะไร อยู่ที่ไหน · แบบไหนเรียกว่าเสร็จ |

**ลำดับการเขียนที่เร็วที่สุด** · 1 เขียน Output ก่อน → 2 แล้วค่อยเขียน Process → 3 ปิดท้ายด้วย Input

### SKILL.md ตัวจริง

```markdown
---
name: weekly-sales-report
description: สรุปยอดขายรายสัปดาห์จากไฟล์ csv
  ใช้เมื่อผู้ใช้ขอ "สรุปยอดสัปดาห์นี้"
---

## Input
- ไฟล์ csv ในโฟลเดอร์ data/ ชื่อขึ้นต้นด้วย sales-
- ถ้ามีหลายไฟล์ ให้ถามก่อนว่าจะใช้ไฟล์ไหน

## Process
1. อ่านไฟล์ แล้วบอกจำนวนแถวกับช่วงวันที่
2. รวมยอดตามสาขา และเทียบกับสัปดาห์ก่อน
3. ถ้าสาขาไหนตกเกิน 10% ให้ดึงรายการสินค้า
   ที่ตกมากที่สุด 5 อันดับของสาขานั้นมาด้วย
4. ห้ามเดาตัวเลขที่ไม่มีในไฟล์

## Output
- ไฟล์ reports/YYYY-WW.md
- ขึ้นต้นด้วยสรุป 3 บรรทัด แล้วค่อยตาราง
- ปิดท้ายด้วยสิ่งที่ข้อมูลยังตอบไม่ได้
```

| บรรทัด | ทำไมถึงเขียนแบบนั้น |
|---|---|
| `name` | ชื่อที่เรียกใช้ ใช้ตัวพิมพ์เล็กและขีดกลาง |
| `description` | **สำคัญที่สุด** — Agent อ่านบรรทัดนี้เพื่อตัดสินว่าจะหยิบ Skill นี้ไหม ต้องมีคำที่ผู้ใช้พูดจริง |
| `## Input` | ระบุว่าต้องมีอะไรก่อนเริ่ม และถ้าไม่ครบให้ถาม ไม่ใช่เดา |
| Process ข้อ 3 | เงื่อนไขแบบ “ถ้า…ให้…” คือจุดที่ Skill เก่งกว่า Prompt ธรรมดา |
| Process ข้อ 4 | ข้อห้ามหนึ่งบรรทัด กันความเสียหายได้มากกว่าคำอธิบายสิบบรรทัด |
| `## Output` | บอกที่เก็บและรูปแบบ เพื่อให้ผลลัพธ์เหมือนเดิมทุกครั้ง |

> ทั้งไฟล์ยาวไม่เกินหนึ่งหน้าจอ — ยาวกว่านั้นแปลว่ากำลังเขียนคู่มือ ไม่ใช่ Skill

### เขียนอย่างไรให้ Agent ทำตามได้

| กว้างจนทำตามไม่ได้ | ชัดพอที่จะตรวจได้ |
|---|---|
| “สรุปให้ดี ๆ” | ขึ้นต้นด้วยสรุป 3 บรรทัด แล้วตารางตามสาขา ปิดท้ายด้วยข้อจำกัด |
| “ตรวจข้อมูลก่อน” | บอกจำนวนแถวและช่วงวันที่ที่อ่านได้ ก่อนเริ่มคำนวณทุกครั้ง |
| “ถ้าผิดปกติให้บอก” | ถ้ายอดสาขาไหนตกเกิน 10% ให้ดึง 5 อันดับสินค้าที่ตกมากที่สุดมาด้วย |
| “อย่ามั่ว” | ห้ามใส่ตัวเลขที่ไม่มีในไฟล์ · ถ้าข้อมูลขาด ให้เขียนว่า “ไม่มีข้อมูล” |
| “เก็บไว้ให้เรียบร้อย” | เขียนลง `reports/YYYY-WW.md` · ถ้ามีไฟล์เดิมอยู่แล้ว ให้ถามก่อนเขียนทับ |

> **กฎเดียวที่ใช้ตัดสิน** — อ่านแล้วบอกได้ไหมว่า Agent “ทำตาม” หรือ “ไม่ทำตาม” ถ้าเถียงกันได้ แปลว่ายังไม่ชัดพอ

### Skill จะถูกเรียกใช้ก็ต่อเมื่อ Agent หามันเจอ

| ผู้ใช้พิมพ์จริง | `description` ต้องมีคำพวกนี้ |
|---|---|
| “ขอสรุปยอดสัปดาห์นี้หน่อย” | สรุปยอดขาย · รายสัปดาห์ · weekly sales |
| “ทำรายงานให้ทีขายอาทิตย์ที่แล้ว” | รายงาน · ยอดขาย · สัปดาห์ที่แล้ว |
| “sales report สัปดาห์นี้” | sales report · csv · ยอดตามสาขา |

> **วิธีทดสอบที่เร็วที่สุด** — ปิดแล้วเปิดใหม่ พิมพ์ประโยคที่จะพูดจริงในวันทำงาน ถ้ามันไม่หยิบ Skill ขึ้นมาเอง ให้ไปแก้ `description` ไม่ใช่แก้ขั้นตอน

### จาก Skill ส่วนตัว สู่ของที่ทีมใช้ร่วมกัน

1. เก็บไว้ที่เดียวกับโค้ดหรือเอกสารของทีม — ไฟล์เดียว แก้ที่เดียว
2. ให้เพื่อนลองใช้โดยที่เราไม่อธิบายอะไรเลย — ถ้าต้องอธิบาย แปลว่ายังเป็นแค่โน้ตของเรา
3. จดจุดที่เพื่อนสะดุด แล้วแก้ที่ Skill ไม่ใช่บอกปากเปล่า
4. ตั้งรอบทบทวนสั้น ๆ เดือนละครั้ง

## Mini Session · MCP (21:55 – 22:00)

**Model Context Protocol** คือมาตรฐานกลางสำหรับเชื่อม Agent เข้ากับ Tools และ Data Sources ภายนอก

1. ต่อเครื่องมือใหม่เข้ากับ Agent โดยไม่ต้องเขียนวิธีเชื่อมต่อเองทุกครั้ง — ต่อครั้งเดียว ใช้ได้กับ Agent ทุกตัวที่รองรับ
2. ระบบภายนอกประกาศความสามารถของตัวเองในรูปแบบเดียวกัน — Agent รู้เองว่าเครื่องมือนั้นทำอะไรได้
3. เปลี่ยน Model หรือ Agent ได้ โดยเครื่องมือที่ต่อไว้ยังใช้ได้เหมือนเดิม
4. เป็นพื้นฐานที่คืนที่ 4 จะใช้ต่อ เมื่อ Agent เริ่มทำงานเป็นทีม

### ทำไมต้องมีมาตรฐานกลาง

| ก่อนมี MCP · ต่อเองทุกคู่ | มี MCP · ต่อผ่านมาตรฐานเดียว |
|---|---|
| Agent A/B/C × Jira/Drive/DB | Agent A/B/C → **MCP** → Jira/Drive/DB |
| 3 × 3 = 9 วิธีเชื่อมต่อที่ต้องดูแลเอง | 3 + 3 = 6 การต่อ และเพิ่มของใหม่ได้โดยไม่กระทบของเดิม |

> เหมือนพอร์ต USB — ไม่ได้ทำให้อุปกรณ์เก่งขึ้น แต่ทำให้เสียบอะไรก็ได้โดยไม่ต้องหาสายเฉพาะรุ่น

### MCP ใช้จริงหน้าตาเป็นแบบไหน

| งานเอกสาร | งานพัฒนา | งานข้อมูล |
|---|---|---|
| ค้นไฟล์ใน Drive ของทีม | อ่าน Issue และ Pull Request | Query ฐานข้อมูลตามสิทธิ์ |
| อ่านสเปกแล้วสรุปให้ | ดูสถานะ Build ล่าสุด | ดึงตัวเลขมาทำรายงาน |
| เขียนสรุปกลับลงที่เดิม | เปิด Ticket ให้อัตโนมัติ | ไม่ต้อง export เป็น csv ก่อน |

> **ข้อควรระวังที่ต้องพูดถึงเสมอ** — ต่อ MCP หนึ่งตัว = ให้สิทธิ์เข้าถึงระบบจริงหนึ่งระบบ
> ดูก่อนว่าใครเขียน ขอสิทธิ์อะไร และถอดออกได้ไหม · เริ่มจาก server ที่อ่านอย่างเดียว แล้วค่อยเปิดสิทธิ์เขียนเมื่อมั่นใจ
