## Session 7 · Planning & Agent Workflow (20:00 – 20:30)

### ทำไมงานใหญ่ถึงพังบ่อยกว่างานเล็ก

| | สั่งรวดเดียว · Agent ที่เดาทางเอง | แตกเป็นขั้น · Agent ที่หยุดให้ตรวจได้ |
|---|---|---|
| รู้ว่าผิดตอนไหน | ตอนอ่านผลลัพธ์สุดท้าย | ตอนจบขั้นที่ผิด |
| แก้แล้วเสียเวลาเท่าไร | รันใหม่ทั้งงาน | รันใหม่เฉพาะขั้นนั้น |
| เอาไปทำซ้ำได้ไหม | ต้องนึกเองว่าเคยสั่งอะไร | มีลำดับขั้นเป็นไฟล์อยู่แล้ว |

### แผนที่ใช้ได้จริง มีสามส่วน
Agent วางแผนไม่เป็น ไม่ใช่เพราะโง่ — แต่เพราะเราไม่ได้บอกว่าอะไรคือ “เสร็จ”

| ส่วน | ตัวอย่าง | เกณฑ์ |
|---|---|---|
| **GOAL** · ปลายทางคืออะไร | ได้ไฟล์ `proposal.md` ที่ลูกค้าอ่านแล้วตัดสินใจได้ | เขียนเป็นสิ่งที่เปิดดูได้ ไม่ใช่ความรู้สึก — “ครบถ้วน” ไม่ใช่เป้าหมาย |
| **STEPS** · ต้องผ่านอะไรบ้าง | 1 รวบรวมข้อมูลลูกค้า · 2 วิเคราะห์ความต้องการ · 3 ร่างข้อเสนอ · 4 ตรวจตัวเลขและเงื่อนไข | แต่ละขั้นต้องมีผลลัพธ์ของตัวเอง ที่ขั้นถัดไปหยิบไปใช้ได้ทันที |
| **DONE** · รู้ได้ยังไงว่าเสร็จ | ทุกตัวเลขมีที่มา · ไม่มีหัวข้อไหนเว้นว่าง · มีรายการสิ่งที่ยังไม่รู้ | เกณฑ์ที่เถียงกันไม่ได้ ถ้าอ่านแล้วยังตีความได้สองแบบ แปลว่ายังไม่ใช่เกณฑ์ |

> เขียนสามส่วนนี้ก่อนพิมพ์คำสั่งแรก ใช้เวลา 2 นาที — ประหยัดการรันซ้ำได้ทั้งคืน

### เดินตาม Workflow จริง หนึ่งงาน
โจทย์ · “ทำสรุปคู่แข่งสามรายให้ทีมขาย ภายในวันนี้”

| ขั้น | Agent ทำอะไร | ผลลัพธ์ที่ต้องได้ | ถ้าไม่ผ่านทำอย่างไร |
|---|---|---|---|
| 01 | สรุปโจทย์เป็นแผนย่อยแล้วรอเราตอบ ok | แผน 4–6 ข้อที่เราอ่านแล้วเห็นภาพ | แก้แผนตรงนี้ ยังไม่ให้เริ่มทำ |
| 02 | ค้นข้อมูลคู่แข่งทีละราย แล้วบันทึกแหล่งที่มา | ไฟล์ `research/` รายละไฟล์ พร้อมลิงก์ | ขาดรายไหน ให้รันซ้ำเฉพาะรายนั้น |
| 03 | เทียบราคาและจุดขาย แล้วตัดสิ่งที่ไม่เกี่ยว | ตารางเปรียบเทียบที่มีแต่ข้อมูลที่ใช้จริง | ถ้าทุกช่องเต็มหมด แปลว่ายังไม่ได้ตัด |
| 04 | ร่างสรุปหนึ่งหน้าสำหรับทีมขาย | ไฟล์ `summary.md` ที่อ่านจบใน 2 นาที | ยาวเกินให้สั่งตัด ไม่ใช่สั่งเขียนใหม่ |
| 05 | ตรวจย้อนว่าทุกข้ออ้างมีที่มาในไฟล์ `research` | รายการข้อที่ตรวจแล้ว และข้อที่ยังไม่แน่ใจ | เจอข้อที่ไม่มีที่มา ให้ถอดออก |

> สังเกตขั้นที่ 1 — Agent หยุดรอเรา นั่นคือจุดที่ถูกที่สุดในการแก้ทั้ง Workflow

### งานแบบนี้ แตกเป็นกี่ขั้น

| งาน | กี่ขั้น | แตกอย่างไร |
|---|---|---|
| “ทำรายงานประจำเดือน” | 4 ขั้น | ดึงข้อมูล → รวมยอด → เทียบเดือนก่อน → เขียนสรุป |
| “ตอบอีเมลลูกค้าฉบับนี้” | 1 ขั้น | งานเดียวจบ อย่าแตกให้มันยุ่งกว่าเดิม |
| “ย้ายเอกสารทีมขึ้นระบบใหม่” | หลายขั้น + วนซ้ำ | สำรวจ → จัดหมวด → ย้ายทีละหมวด → ตรวจทีละหมวด |
| “หาสาเหตุที่ยอดตก” | 3 ขั้น | ตั้งสมมติฐาน → หาข้อมูลมาหักล้าง → สรุปเฉพาะที่เหลือรอด |
| “เขียนบทความจากงานวิจัย” | 5 ขั้น | อ่าน → สกัดประเด็น → วางโครง → ร่าง → ตรวจข้อเท็จจริง |
| “เช็กว่าเว็บล่มหรือเปล่า” | 1 ขั้น | งานที่จบในคำสั่งเดียว ไม่ต้องมี Workflow |

> **เกณฑ์ตัดสิน** — ถ้าขั้นนั้นไม่มีอะไรให้เราเปิดดู มันไม่ใช่ขั้น มันคือคำอธิบาย

### สี่เสาที่ทำให้ Workflow เชื่อถือได้

| เสา | คืออะไร | ใส่อย่างไร |
|---|---|---|
| **Error Handling** | บอกล่วงหน้าว่าถ้าขั้นไหนล้ม ให้ทำอะไรต่อ | ไฟล์หาย ให้บอกแล้วหยุด · API ล่ม ให้ข้ามไปขั้นอื่นก่อน · ข้อมูลไม่ครบ ให้ถามกลับ |
| **Retry** | ลองใหม่แบบมีเงื่อนไข ไม่ใช่วนซ้ำวิธีเดิมไปเรื่อย ๆ | ลองได้ไม่เกิน 2 ครั้ง · รอบสองต้องเปลี่ยนวิธี · ครบแล้วยังไม่ได้ ให้รายงาน |
| **Verification** | ตรวจผลลัพธ์ด้วยเกณฑ์ ก่อนส่งให้ขั้นถัดไป | เทียบกับเกณฑ์ที่เขียนไว้ · สุ่มตรวจย้อนกลับ 2 ข้อ · ให้ Agent คนละตัวตรวจ |
| **Human-in-the-loop** | จุดที่คนต้องอนุมัติ ก่อนงานเดินข้ามไปจุดที่ย้อนยาก | ก่อนส่งออกนอกทีม · ก่อนเขียนทับของเดิม · ก่อนใช้เงินหรือให้สัญญา |

### ใส่จุดหยุดไว้ตรงไหนบ้าง

1. **หลังวางแผน ก่อนเริ่มลงมือ** — จุดที่ถูกที่สุด แก้หนึ่งบรรทัดแทนการรันใหม่ทั้งงาน
2. **ก่อนการกระทำที่ย้อนกลับไม่ได้** — ส่งอีเมล ลบไฟล์ จ่ายเงิน เปลี่ยนสถานะในระบบจริง
3. **เมื่อ Agent เจอทางแยกที่ข้อมูลไม่พอ** — ให้มันถามพร้อมตัวเลือก ไม่ใช่เลือกเองแล้วเขียนเหตุผลสวย ๆ
4. **ก่อนส่งผลงานออกนอกทีม** — คนเซ็นชื่อรับผิดชอบยังเป็นคน · Agent ร่างได้ แต่ไม่ได้อนุมัติ

> จุดหยุดที่ดีใช้เวลาคนไม่เกิน 30 วินาทีต่อครั้ง — ถ้านานกว่านั้น แปลว่าเราขอให้คนทำงานแทน Agent

### งานแบบไหนควรทำเป็น Workflow

| ✓ สัญญาณว่าควรทำ | ✕ สัญญาณว่ายังไม่ต้อง |
|---|---|
| มีหลายขั้นที่ต้องทำตามลำดับ | สั่งครั้งเดียวแล้วจบได้ |
| ขั้นกลางมีโอกาสผิดโดยที่เรายังไม่เห็น | ผิดแล้วรู้ทันทีจากผลลัพธ์ |
| งานใช้เวลานานจนไม่อยากรันซ้ำทั้งหมด | รันใหม่ทั้งงานใช้เวลาไม่ถึงนาที |
| มีจุดที่ต้องให้คนอนุมัติระหว่างทาง | ไม่มีอะไรที่ย้อนกลับไม่ได้เลย |
| ต้องส่งต่อให้คนอื่นหรือ Agent ตัวอื่นทำต่อ | ทำเองคนเดียวจบในหัวได้ |

### เขียนขั้นตอนให้ตรวจได้

| เขียนแบบนี้ Agent เดาเอง | เขียนแบบนี้ตรวจได้ |
|---|---|
| “ค้นข้อมูลให้ครบ” | ค้นอย่างน้อย 5 แหล่ง แล้วแนบลิงก์ทุกแหล่งใน `research.md` |
| “วิเคราะห์ให้ดี” | เทียบ 3 คู่แข่งในตารางเดียว ช่องละไม่เกิน 1 ประโยค |
| “ถ้าติดปัญหาให้แก้” | ถ้าเปิดลิงก์ไม่ได้ ให้ข้ามและบันทึกไว้ท้ายไฟล์ ห้ามเดาเนื้อหา |
| “ตรวจงานก่อนส่ง” | สุ่มตรวจข้ออ้าง 2 ข้อย้อนกลับไปหาแหล่ง แล้วรายงานผลการตรวจ |
| “สรุปส่งมาให้หน่อย” | เขียน `summary.md` ยาวไม่เกิน 1 หน้า ปิดท้ายด้วยสิ่งที่ยังไม่รู้ |

### สี่อาการของ Workflow ที่พัง

| อาการ | ทางแก้ |
|---|---|
| Agent ข้ามขั้นแล้วไปตอบตอนจบเลย | สั่งให้ส่งผลลัพธ์ของแต่ละขั้นเป็นไฟล์ แล้วรอ ok ก่อนเดินขั้นถัดไป |
| รันไปเรื่อยจน Context เต็มแล้วลืมโจทย์ | ให้เขียนผลแต่ละขั้นลงไฟล์ แล้วขั้นถัดไปอ่านจากไฟล์ ไม่ใช่จากแชท |
| ขั้นที่ล้มแล้ววนลองวิธีเดิมไม่จบ | กำหนดจำนวนครั้งไว้ในโจทย์ และบังคับว่ารอบสองต้องเปลี่ยนวิธี |
| ผลออกมาสวยแต่ขั้นกลางไม่ได้ทำจริง | ขอ trace ว่าแต่ละขั้นเรียกเครื่องมืออะไร ได้ไฟล์อะไร แล้วเปิดดูไฟล์เอง |

> ทุกข้อแก้ด้วยหลักเดียวกัน — **ทำให้แต่ละขั้นทิ้งหลักฐานไว้ข้างนอกแชท**

## Session 8 · Sub-agents & Multi-Agent (21:15 – 21:35)

### Agent เดียว หรือหลาย Agent

| | Agent เดียว · ตัวเดียวทำครบทุกอย่าง | ทีม Agent · แบ่งบทบาทแล้วส่งงานกัน |
|---|---|---|
| ความยาวของงาน | จบในไม่กี่สิบขั้น | ยาวจนจำต้นทางไม่ไหว |
| ความต่างของทักษะ | ใช้วิธีคิดแบบเดียวตลอด | ค้น เขียน ตรวจ คนละแบบกัน |
| ใครตรวจใคร | ตรวจงานตัวเอง | คนละตัวกับคนทำ |

### เมื่อไหร่ควรแบ่งงาน
หลาย Agent ไม่ได้แปลว่าดีกว่า — แปลว่าแพงกว่าและช้ากว่า ถ้าไม่มีเหตุผลรองรับ

| ✓ สัญญาณว่าควรแบ่ง | ✕ สัญญาณว่ายังไม่ต้อง |
|---|---|
| งานยาวจน Context เต็มก่อนจบ | งานจบได้ในรอบเดียว |
| ต้องมีคนตรวจที่ไม่ใช่คนทำ | ผลลัพธ์ตรวจเองได้จากไฟล์ |
| แต่ละส่วนใช้เครื่องมือคนละชุดกัน | ใช้เครื่องมือชุดเดียวทั้งงาน |
| บางส่วนทำขนานกันได้จริง | ทุกขั้นต้องรอขั้นก่อนหน้า |
| อยากเปลี่ยนแค่บางบทบาทโดยไม่รื้อทั้งระบบ | ยังไม่รู้เลยว่าขั้นตอนที่ดีคืออะไร |

> ถ้ายังตอบไม่ได้ว่า “ตัวไหนรับอะไร ส่งอะไร” ให้กลับไปทำ Workflow ตัวเดียวให้นิ่งก่อน

### สามส่วนของการส่งงานระหว่าง Agent

| ส่วน | คืออะไร | คำถามที่ต้องตอบให้ได้ |
|---|---|---|
| **ROLE** · แต่ละตัวเป็นใคร | หน้าที่เดียวที่ชัด เครื่องมือเท่าที่จำเป็น ข้อห้ามที่เขียนตรง ๆ | ตัวนี้ทำอะไรได้ · อะไรที่ห้ามทำเด็ดขาด |
| **HANDOFF** · ส่งอะไรให้กัน | รูปแบบข้อมูลที่ตกลงกันไว้ล่วงหน้า ปกติคือไฟล์ในโฟลเดอร์ | ไฟล์ชื่ออะไร · มีหัวข้ออะไรบ้าง · ใครเขียน |
| **GATE** · ผ่านเมื่อไหร่ | เกณฑ์ที่บอกว่างานของตัวก่อนหน้าใช้ได้แล้ว | ตีกลับเมื่อไหร่ · ตีกลับแล้วใครแก้ |

**ลำดับการออกแบบที่เร็วที่สุด** · 1 เขียน Handoff ก่อน → 2 แล้วค่อยเขียน Role → 3 ปิดท้ายด้วย Gate

### ห้าบทบาทของทีม AI
เริ่มจากสามตัวก่อนก็พอ — Researcher, Writer, Reviewer ครอบคลุมงานส่วนใหญ่แล้ว

| บทบาท | หน้าที่ | รายละเอียด |
|---|---|---|
| Orchestrator | รับโจทย์และคุมลำดับ | แตกงาน กระจาย รวมผล และตัดสินใจว่าจะตีกลับไหม |
| Researcher | หาและอ่านข้อมูล | ส่งออกเป็นข้อเท็จจริงพร้อมแหล่งที่มา ไม่ตีความ |
| Analyst | เทียบและตัดสินใจ | รับข้อเท็จจริง ส่งคืนข้อสรุปพร้อมเหตุผลและสิ่งที่ตัดทิ้ง |
| Writer | เรียบเรียงให้คนอ่าน | รับข้อสรุป ส่งคืนร่างตามรูปแบบที่ตกลงไว้ |
| Reviewer | ตรวจและตีกลับ | รับร่าง ส่งคืนรายการจุดแก้ พร้อมบอกว่าข้อไหนบล็อกการส่ง |
| **คุณ (มนุษย์)** | อนุมัติและรับผิดชอบ | ดูผลตรวจแล้วตัดสินใจว่าจะปล่อยงานออกหรือให้แก้ |

> บทบาทที่คนมักลืมใส่คือ **Reviewer** — และมันคือตัวที่เปลี่ยนคุณภาพมากที่สุด

### สี่กับดักของทีม AI

| อาการ | ทางแก้ |
|---|---|
| ทุกตัวได้ Context ก้อนเดียวกันทั้งหมด | ส่งเฉพาะไฟล์ที่ตัวนั้นต้องใช้ — แบ่งบทบาทแล้วแต่ไม่แบ่งข้อมูล ก็ไม่ได้อะไรเพิ่ม |
| Reviewer ผ่านทุกอย่างโดยไม่ค้านอะไรเลย | ให้เกณฑ์ตรวจเป็นข้อ ๆ และบังคับให้รายงานข้อที่ไม่ผ่านอย่างน้อยหนึ่งข้อ |
| ตีกลับไปมาไม่จบ งานวนอยู่ในทีม | กำหนดรอบตีกลับสูงสุด 2 ครั้ง ครบแล้วให้ส่งขึ้นมาให้คนตัดสิน |
| Orchestrator ลงไปทำงานเองแทนที่จะกระจาย | ตัดเครื่องมือของ Orchestrator ให้เหลือแค่การอ่านไฟล์และมอบหมายงาน |

### ออกแบบการส่งงานให้ไม่หลุด

1. ส่งกันด้วยไฟล์ ไม่ใช่ข้อความในแชท — ไฟล์เปิดย้อนดูได้ แก้ได้ และไม่หายไปพร้อม Context
2. ตกลงหัวข้อของไฟล์ไว้ล่วงหน้า — ตัวรับรู้ว่าจะเจออะไร จึงไม่ต้องเดาโครงสร้างทุกครั้ง
3. ทุกไฟล์ต้องบอกว่าใครเขียนและอ้างอิงอะไร — พอผลลัพธ์ผิด เราตามได้ทันทีว่าหลุดที่บทบาทไหน
4. เขียนเงื่อนไขตีกลับไว้ในไฟล์เดียวกัน — Reviewer แค่ชี้ข้อที่ไม่ผ่านตามเกณฑ์ที่ตกลงไว้
