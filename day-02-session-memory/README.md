## Session 3 · Context & Session (20:00 – 20:30)

### Context คืออะไร
ทุกสิ่งที่โมเดลได้เห็นในรอบการทำงานหนึ่งครั้ง — ไม่มากไปกว่านั้น

| # | คำ | ความหมาย |
|---|---|---|
| 01 | Context | คำสั่ง ประวัติการคุย ไฟล์ที่แนบ และผลจาก Tool ทั้งหมดที่ถูกส่งเข้าโมเดลในรอบนั้น |
| 02 | Context Window | เพดานจำนวน Token ที่ใส่ได้ เมื่อเต็ม ของเก่าต้องออกไปเพื่อให้ของใหม่เข้ามา |
| 03 | Conversation History | บทสนทนาที่ถูกส่งกลับเข้าไปใหม่ทุกรอบ นี่คือเหตุผลที่ Agent ดูเหมือน “จำ” ได้ |

### ใน Context หนึ่งรอบมีอะไรบ้าง
คำถามสั้น ๆ หนึ่งคำถาม แต่สิ่งที่ถูกส่งเข้าโมเดลจริง ๆ คือทั้งหมดนี้

| ชิ้นส่วนของ Context | ตัวอย่างในงานจริง | ≈ Token |
|---|---|---|
| คำสั่งประจำตัว | “ตอบเป็นภาษาไทย กระชับ ไม่ต้องเกริ่น” | 300 |
| Memory ที่ถูกอ่านเข้ามา | User Memory + Project Memory | 800 |
| ประวัติการคุย 20 รอบ | ทุกคำถามและคำตอบก่อนหน้าในเรื่องนี้ | 12,000 |
| ไฟล์ที่แนบ | `sales_q3.csv` · 400 แถว | 6,000 |
| ผลจาก Tool | ผลค้นหา 5 รายการที่ Agent เพิ่งดึงมา | 3,000 |
| | **รวม** | **≈ 22,100** |

> คำถามของเราเองยาวแค่ 1 บรรทัด — ที่เหลือคือของที่ถูกแบกมาด้วย
> เมื่อชนเพดาน ประวัติที่เก่าที่สุดถูกตัดออกก่อน แล้ว Agent ก็ “ลืม”
> *(ตัวเลขเป็นตัวอย่างโดยประมาณ)*

### Session คือขอบเขตของงาน

- **Session** — พื้นที่ทำงานหนึ่งเรื่อง มีจุดเริ่ม มีประวัติของตัวเอง และมีจุดจบ งานคนละเรื่องควรอยู่คนละ Session เพื่อไม่ให้บริบทปนกัน
- **Session Persistence** — Hermes บันทึก Session ไว้ให้กลับมาทำงานต่อได้ แต่สิ่งที่กลับมาคือ *ประวัติของงานนั้น* ไม่ใช่ความรู้เกี่ยวกับตัวเราที่ใช้ข้ามงานได้

```
เริ่มงาน → คุย · ทำงาน · สะสมประวัติ → ปิด Session
              (ประวัติถูกเก็บไว้ · แต่ไม่ใช่ความรู้เรื่องเรา)
```

### Context Management · สี่ข้อ
Context เป็นทรัพยากรจำกัด บริหารมันเหมือนบริหารพื้นที่บนโต๊ะทำงาน

1. เริ่ม Session ใหม่เมื่อเปลี่ยนเรื่อง ดีกว่าลากบริบทเก่าติดไปทั้งหมด
2. สรุปงานที่ยาวให้สั้นลง แล้วเก็บเฉพาะข้อสรุปไว้ใน Context
3. อ้างถึงไฟล์แทนการวางเนื้อหาทั้งไฟล์ลงในบทสนทนา
4. ข้อมูลที่ต้องใช้ทุกครั้ง ไม่ควรอยู่ใน Context ควรอยู่ใน Memory

### เปลี่ยนวิธี ไม่ต้องเปลี่ยนงาน

| ✕ แบบที่ทำให้ Context บวม | ✓ แบบที่ควบคุมได้ |
|---|---|
| วาง `sales_q3.csv` ทั้ง 400 แถวลงในแชท | “อ่านไฟล์ `sales_q3.csv` แล้วสรุปยอดรายเดือน” |
| คุยเรื่องเดิมยาว 40 รอบจนบริบทเริ่มหาย | “สรุปข้อตกลงเป็น 5 ข้อ” แล้วเปิด Session ใหม่ด้วยสรุปนั้น |
| บอกชื่อ บทบาท และสไตล์ที่ชอบใหม่ทุกครั้ง | เขียนลง User Memory ครั้งเดียว แล้วไม่ต้องบอกอีก |

## Session 4 · Persistent Memory (21:05 – 21:30)

### ความจำสองระยะ

| | Short-term Memory | Long-term Memory |
|---|---|---|
| อยู่ที่ไหน | ใน Context ของรอบนั้น | ถูกเขียนลงไฟล์ |
| อยู่ได้นานแค่ไหน | หายไปเมื่อ Context ถูกตัดหรือ Session จบ | ถูกอ่านกลับเข้ามาทุกครั้งที่เริ่มงาน |
| เหมาะกับอะไร | สิ่งที่ใช้เดี๋ยวนี้ | สิ่งที่จริงเสมอ ไม่ใช่สิ่งที่จริงแค่วันนี้ |

### Memory สามชนิด
แยกด้วยคำถามเดียว — ข้อมูลนี้จริงกับใคร กับเรา กับโปรเจกต์ หรือกับวิธีทำงาน

| ชนิด | เก็บอะไร |
|---|---|
| **User Memory** | ตัวตนและความชอบของเรา ชื่อ บทบาท ภาษาที่ใช้ รูปแบบผลลัพธ์ที่ต้องการ — ใช้ได้กับทุกโปรเจกต์ |
| **Project Memory** | บริบทของงานหนึ่งงาน โครงสร้างไฟล์ ข้อตกลง คำศัพท์เฉพาะ และข้อจำกัดของโปรเจกต์นั้น |
| **Procedural Memory** | วิธีทำงานที่ทำซ้ำได้ ขั้นตอนที่เราอยากให้ Agent ทำเหมือนกันทุกครั้ง — ต่อยอดเป็น **Skills** ในคืนที่ 3 |

### อะไรควรอยู่ใน Memory

| ✓ ควรเก็บ | ✕ ไม่ควรเก็บ |
|---|---|
| ข้อเท็จจริงที่จริงเสมอ — บทบาท ทีม ภาษา | รายละเอียดของงานเฉพาะรอบเดียว |
| ความชอบที่ต้องทำซ้ำ — รูปแบบไฟล์ โครงสร้างรายงาน | ข้อมูลที่เปลี่ยนบ่อย เช่น สถานะงานรายวัน |
| ข้อตกลงของโปรเจกต์ — คำศัพท์ กฎการตั้งชื่อ | ความลับ รหัสผ่าน และ API Key |
| ข้อผิดพลาดที่ไม่ต้องการให้เกิดซ้ำ | ประวัติบทสนทนาทั้งหมดแบบดิบ |

### เขียนอย่างไรให้ Agent ใช้ได้จริง

| กว้างเกินจนใช้ไม่ได้ | แคบพอที่จะตรวจได้ |
|---|---|
| “ชอบงานเป็นระเบียบ” | รายงานทุกฉบับขึ้นต้นด้วยสรุป 3 บรรทัด แล้วค่อยลงรายละเอียด |
| “ทำงานสาย data” | ดูแล pipeline ที่ดึงยอดขายสาขาเข้า warehouse ทุกคืน |
| “อย่าตอบยาว” | ตอบไม่เกิน 5 บรรทัด ถ้ายาวกว่านั้นให้ถามก่อนว่าจะลงลึกไหม |
| “ใช้ภาษาสุภาพ” | ลงท้ายด้วย ครับ · ไม่ใช้คำแสลง · ไม่เรียกผู้ใช้ว่า “คุณลูกค้า” |

> **กฎเดียวที่ใช้ตัดสิน** — อ่านแล้วบอกได้ไหมว่า Agent “ทำตาม” หรือ “ไม่ทำตาม”
